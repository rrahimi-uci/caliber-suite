# Protected-effect paths

Every code path in `caliber/src/caliber/` that can change an external system or send data out of the platform, with the guard it has today and what the Beta does with it. It is the source for the dispatcher's path matrix (#520), for ADR 0002's ownership table (#565) and for the reference profile's refusal list (#532, #534). This file is checked by `caliber/tests/test_protected_effect_inventory.py`: every source file that contains an outbound-effect primitive must have a row, every function that contains one is pinned to a row in `caliber/tests/fixtures/protected_effect_primitives.json` (so a new primitive in a file or function that already has a row fails until the pin is updated on purpose), every row must name a real file and function, the counts below must match the table, no row may carry an undecided note, and the copy shipped in the wheel (`caliber/src/caliber/effects/protected-effect-paths.md`) must equal this one. When you add a path that reaches the outside world, add its row here, pin it, and copy the file over the packaged one.

Written for the 2026-10-26 tree and revised for #641 on 2026-10-28 and #728 on 2026-10-30 and B04.2, B04.3, B04.4 and B04.5 on 2026-10-31: 135 rows. By current guard: none 98, approval 23, egress 11, ledger 3. By disposition: dispatch 42, refuse 26, exempt 67. By effect class: irreversible_write 68, reversible_write 37, export 14, read 16.

## How to read the table

- **effect class**: `read` changes nothing outside the platform; `reversible_write` changes state the platform versions or can undo with a compensating call (MLflow prompt versions and aliases, workflow working-directory files); `export` copies data outside the platform boundary or produces a deployable artifact; `irreversible_write` changes a third party's state or state that has no reliable undo (webhooks, remote tools, GitHub, object deletes and unversioned overwrites, arbitrary code). When unsure, the stricter class is used.
- **current guard**: the strongest guard that applies on the production path, in the order `ledger`, `approval`, `egress`, `none`. `ledger` is the effect ledger (a claim before the call, so a restarted run does not repeat it), `approval` a human or `requires_approval` gate, `egress` an address policy checked when the connection is made. Any other guard (module allowlist, route scope, preview wrapper, sandbox) and any condition on the guard is in the notes.
- **D3 disposition**: `dispatch`: an effect a workflow node, model tool call or agent can trigger, which D3 routes through the dispatcher. `refuse`: a path the reference profile must not allow (arbitrary code, module import, runnable exports, an unauthenticated server, host-file reads that export unconfined host data, database writes through the first-party MCP server). `exempt`: platform-internal bookkeeping or an operator-initiated action that no model proposal or workflow effect node can reach, authorized by project RBAC or configuration, or a helper reached only through a `dispatch` row (the notes name it); the notes say why. An exempt row is not a clean bill of health: it only means the dispatcher does not wrap it.
- **tool names**: the registered tool, OpenAPI operation or MCP tool names that reach the entry point, `-` when the entry point is reached by dynamic names.

## Scope decisions

- Included: calls to MLflow, the object store, GitHub, webhooks and remote tools, vector memory, subprocesses and dynamic imports. Excluded: database-only bookkeeping writes (the effect ledger, audit rows, sessions, the DB-backed secret store).
- Model-provider calls (OpenAI and Anthropic SDK clients, the memory service's inference and embedding calls, judges) are not rows: they send prompts out of the platform, use SDK clients that bypass `caliber.egress`, and belong to the model-budget and egress work in B08 (#526) and B12 (#534). They are listed in the findings below so they are not forgotten.
- A few rows touch only the platform database (EP-010, EP-076, EP-083). They are listed because they change what the platform serves or runs on behalf of a node or a promotion, not because they leave the platform.
- Several rows share an entry point (for example five branches of `_run_node`); the `id` is the unique key and the notes name the branch.

## Findings the table makes visible

Each of these is tracked for resolution in B04 or B12; none is fixed by this document.

- The effect ledger protects only the queued-worker path. `_perform_guarded_effect` gets a ledger only from the worker (`orchestrator/workflow_run_worker.py:1629`); the synchronous run route and exported workflows get egress only, and MCP, OpenAPI, knowledge-build and output-bucket effects never use it, so a worker restart can repeat them.
- Approval for tool nodes is off by default: the node gate needs `CALIBER_WORKFLOW_RUN_RUNTIME_APPROVALS_ENABLED`, which defaults to false (`config.py:601`).
- The standalone tool-sandbox server (`tool_sandbox/server.py`) runs arbitrary source or modules with no authentication or scope check.
- In the `auto_all` and `full_autonomy` Aria modes an agent can invoke write and external-action OpenAPI tools, run workflows, run draft source in the sandbox and publish drafts (`assistant/agent_tools.py`).
- The GitHub transport and the platform event webhooks (`events/webhooks.py`) do not pass through `caliber.egress`.
- Host-file read tools in `workflows/demo_tools.py` read any path with no `confine_to_file_root`. Decided in #641: EP-055 is `refuse`, so the reference profile does not export host files until the tools confine reads to a configured root.
- Workflow export bundles embed generated Python.
- Model-provider calls bypass `caliber.egress` (see the scope decisions).
- A tool's name is not its identity. `CaliberToolRegistry` is unique on (name, version), so a custom tool could be called `grep_files`. Resolved in #641: `POST /tools`, the OpenAPI tool-draft publish route and `AssistantPublisher._publish_tool` refuse every built-in name with `reserved_tool_name` (409 from the routes, `success: false` from the publisher; case, whitespace, the `tool.` prefix and the `.vN` suffix are ignored), and `effect_class` still trusts the table only when the caller states the tool is one CALIBER ships. A registry row gets that statement from `effects.inventory.effect_class_for_registry_tool` (and `tool_disposition_for_registry_tool`), which check **every** field the seed writes (`workflows.builtin_tools.is_builtin_tool`: name, owner `@caliber`, version `1.0`, a callable named like the tool, and the tool's own module from `BUILTIN_TOOL_MODULE_BY_NAME`). A production call that passes a constant `caliber_defined`, a string constant for an identity field, a `**kwargs` expansion or a `functools.partial` of these lookups fails `tests/test_protected_effect_inventory.py`. **A dispatch site must pass the registry row's own name, owner, module, callable and version, read from the database for the tool being run, never `local_name` or `resolved_name` of a manifest binding:** `IRToolBinding` and `ToolRegistryEntry` deliberately carry no owner (the IR is written into generated exports field by field, so an owner there would be data a bundle author controls, and adding the field would change every export). A tool registered under a built-in's name before the rule existed is not migrated: it stays untrusted (fail-closed), and `register_builtin_tools` logs it and writes one `flag_reserved_tool_name` audit record, which also says when it blocks the real built-in from being seeded. B07 (#524) and B08 (#526) call the helpers.
- The first-party PostgreSQL MCP server (`mcp_servers/db/`) can create tables and write rows (EP-114); once an admin registers it, a model's tool call reaches it through the MCP rows. Decided in #641: EP-114 is `refuse` and lists its write tools by name, so the reference profile does not allow database writes through MCP until they are routed through the dispatcher with an exact-intent approval.
- Optimizer plugins execute inside the control plane once their distribution is allowlisted (EP-121).
