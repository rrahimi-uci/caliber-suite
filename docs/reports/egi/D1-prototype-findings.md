# D1 prototype findings

## B04 prototype

Spike for #625: persist a proposal, derive a stable key from `(run, node, canonical args)`, dispatch with the key and the expected case version, lose the response after the downstream commits, dispatch again with the same key. Code: `caliber/tests/egi_scenarios/prototype/dispatch_spike.py`; tests: `caliber/tests/egi_scenarios/test_prototype_lost_receipt.py` (23 cases on SQLite and PostgreSQL). Both are disposable and #520 task 1 deletes them.

**Result.** After `drop_response_after_commit` the first dispatch raises `httpx.RemoteProtocolError`, the downstream has already committed (`mutations() == 1`), and sending the same proposal again with the same key returns 200 with the stored answer and leaves `mutations() == 1`. (In the committed tests the proposal's state after the loss is `unknown`, because #626's state machine records an ambiguous dispatch that way; before #626 it stayed `dispatched`.) The control run (a different key for the same request) produces a second mutation. The claim holds on both dialects.

**Effort.** About 0.75 hour of agent wall-clock, from reading the issue to the second green run, including reading the executor and runtime code below. That is agent time with the downstream and contracts already in place, not a person-hour figure; #572 should not scale #520 from it directly.

**Measured round trip** (`cd caliber && PYTHONPATH=src:. python -m tests.egi_scenarios.prototype.measure`: 40 dispatches of each kind against the downstream process on loopback, SQLite proposal store; median / max): first dispatch 3.9 ms / 5.7 ms; replay of the same key 3.4 ms / 5.0 ms; dispatch whose response is dropped 3.8 ms / 6.0 ms (one run on a laptop; the numbers vary by a millisecond or so between runs). The cost of the stable-key design is not in the network call; a scenario can run hundreds of dispatches in a second.

### What #520 must change

- `caliber/src/caliber/integrations/openapi/executor.py::execute_openapi_http_tool` (lines 115–232). It sends an idempotency key only when the operation's `backend_config` binds `idempotency_key_header` **and** the caller put `input_data["idempotency_key"]` in the input (lines 164–168); nothing in the platform derives that key. It has no notion of an expected resource version: `If-Match` could travel only as a free-form `header_params` entry. The dispatcher must derive the key and the version from the persisted proposal and pass them as dedicated inputs, not through caller-supplied header maps.
- Same function, retry loop (lines 178–215). A transport error is retried up to `max_attempts` (at most 5) when a key is bound, with bounded backoff. That is safe only because the downstream honours the key, which this spike confirms for one downstream. The dispatcher should own retries and record each attempt against the proposal; today the attempt count is only returned in the result (`attempts`).
- Same function, result (lines 217–232). It returns `status_code` (so a 201 and a 200 replay are distinguishable), `text`, `json`, `headers`, but nothing interprets them: no notion of a replay, no receipt, no downstream request id. A receipt needs the status, the request id and whether the answer was a replay, so the dispatcher must keep them.
- `caliber/src/caliber/workflows/runtime.py::_perform_guarded_effect` (line 4344). With a ledger, it claims `(node_id, payload)` before the call and, on an *ambiguous* failure (anything other than `ConnectionError`, `ConnectionRefusedError`, `FileNotFoundError`; see `_DEFINITIVE_EFFECT_FAILURES`, line 4393), leaves the claim `in_progress`, so the next attempt raises `IndeterminateEffectError` and the node fails as `ToolExecutionError` (lines 4370–4375). The default sender it wraps (`_default_webhook_sender`, line ~2945) puts only the caller's headers on the request, so it never sends an idempotency key, and it lets `httpx` exceptions propagate, which are not the builtin `ConnectionError`s of `_DEFINITIVE_EFFECT_FAILURES`: in practice every transport failure there is ambiguous. (A builtin `ConnectionResetError` or `BrokenPipeError` is also listed as "definitive" although it can happen after a commit.) For a downstream that supports a stable key, a send with the same key is safe at the downstream, so #520 must replace "indeterminate, give up" with a question to the downstream (query by key) before any further send; #626 builds the `unknown` state and `reconcile` for that, and its transition table makes the bare re-dispatch of an `unknown` proposal illegal on purpose (this spike's test replays with the bare `send`, which proves the downstream behavior, not a state transition).
- `caliber/src/caliber/workflows/effect_ledger.py::effect_key` (line 123). The platform already has an attempt-invariant key, `eff-<56 hex>` over a fingerprint that includes an `occurrence` counter and canonicalises with `ensure_ascii=False, default=str`. The spike's key is a plain sha256 over `run|node|canonical args` with compact separators and no occurrence. The two will disagree on the same effect. #520 should decide one: either reuse `effect_key` (and carry `occurrence` into the proposal) or replace it and migrate the ledger's key column. The spike does not settle which; it shows only that a stable key suffices for the downstream.
- The two call sites of `_perform_guarded_effect` (the webhook and API-request nodes) are the only **ledger-guarded** seams today (`docs/architecture/protected-effect-paths.md` EP-001, EP-002); the inventory lists 39 `dispatch` rows in all, among them the OpenAPI executor (EP-030, no ledger) and MCP. The sync run route attaches no ledger, so it would repeat the effect on a retry.
- The spike's unique `logical_key` makes a second proposal for identical arguments an `IntegrityError` (tested). The platform's `effect_key` carries an `occurrence` counter precisely so a loop that posts the same body twice is two effects; #520 must carry `occurrence` into the key or a legitimate repeat would be rejected as a duplicate.
- The connector experiment (`docs/reports/egi/D1-connector-capability.md`, #567) has the executor-side findings (key plumbing, retry gating, typed errors) that complement these.

### What surprised me

- The downstream's `If-Match` guard alone already refuses a blind second dispatch with a different key (412), because the first commit bumped the case version. It does not help with a lost response: the retry is refused instead of getting the stored answer, and the caller cannot tell "my first attempt committed" from "someone else changed the case". Only the stable key resolves that, so the key is not redundant with the version check (`test_the_expected_version_alone_also_stops_a_blind_second_dispatch`).
- The proposal row must be set to `dispatched` and committed *before* the request leaves; if it were set after, a crash during the call would leave `proposed`, indistinguishable from "never sent".
- A unique `logical_key` column makes proposing the same effect twice an integrity error on both dialects: a duplicate proposal is rejected by the store, not by application code.
- `validate_record("proposal", ...)` (#566) is cheap enough to call on every proposal, and the spike's proposal record validated against the schema on the first run, so the schema fits the fields a dispatch needs (`logical_key`, `intent_hash`, `target`, `expected_resource_version`, `state`).
