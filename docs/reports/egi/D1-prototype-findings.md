# D1 prototype findings

## B04 prototype

Spike for #625: persist a proposal, derive a stable key from `(run, node, canonical args)`, dispatch with the key and the expected case version, lose the response after the downstream commits, dispatch again with the same key. Code: `caliber/tests/egi_scenarios/prototype/dispatch_spike.py`; tests: `caliber/tests/egi_scenarios/test_prototype_lost_receipt.py` (23 cases on SQLite and PostgreSQL). Both are disposable and #520 task 1 deletes them.

**Result.** After `drop_response_after_commit` the first dispatch raises `httpx.RemoteProtocolError`, the downstream has already committed (`mutations() == 1`), and sending the same proposal again with the same key returns 200 with the stored answer and leaves `mutations() == 1`. (In the committed tests the proposal's state after the loss is `unknown`, because #626's state machine records an ambiguous dispatch that way; before #626 it stayed `dispatched`.) The control run (a different key for the same request) produces a second mutation. The claim holds on both dialects.

**Effort.** About 0.75 hour of agent wall-clock, from reading the issue to the second green run, including reading the executor and runtime code below. That is agent time with the downstream and contracts already in place, not a person-hour figure; #572 should not scale #520 from it directly.

**Measured round trip** (`cd caliber && PYTHONPATH=src:. python -m tests.egi_scenarios.prototype.measure`: 40 dispatches of each kind against the downstream process on loopback, SQLite proposal store; median / max): first dispatch 3.9 ms / 5.7 ms; replay of the same key 3.4 ms / 5.0 ms; dispatch whose response is dropped 3.8 ms / 6.0 ms (one run on a laptop; the numbers vary by a millisecond or so between runs). The cost of the stable-key design is not in the network call; a scenario can run hundreds of dispatches in a second.

### What #520 must change

- `caliber/src/caliber/integrations/openapi/executor.py::execute_openapi_http_tool` (lines 115–232). It sends an idempotency key only when the operation's `backend_config` binds `idempotency_key_header` **and** the caller put `input_data["idempotency_key"]` in the input (lines 164–168); nothing in the platform derives that key. It has no notion of an expected resource version: `If-Match` could travel only as a free-form `header_params` entry. The dispatcher must derive the key and the version from the persisted proposal and pass them as dedicated inputs, not through caller-supplied header maps.
- Same function, retry loop (lines 178–215). A transport error is retried up to `max_attempts` (at most 5) when a key is bound, with bounded backoff. That is safe only because the downstream honours the key, which this spike confirms for one downstream. The dispatcher should own retries and record each attempt against the proposal; today the attempt count is only returned in the result (`attempts`).
- Same function, result (lines 217–232). It returns `status_code` (so a 201 and a 200 replay are distinguishable), `text`, `json`, `headers`, but nothing interprets them: no notion of a replay, no receipt, no downstream request id. A receipt needs the status, the request id and whether the answer was a replay, so the dispatcher must keep them.
- `caliber/src/caliber/workflows/runtime.py::_perform_guarded_effect` (line 4344). With a ledger, it claims `(node_id, payload)` before the call and, on an *ambiguous* failure (anything other than `ConnectionError`, `ConnectionRefusedError`, `FileNotFoundError`; see `_DEFINITIVE_EFFECT_FAILURES`, line 4393), leaves the claim `in_progress`, so the next attempt raises `IndeterminateEffectError` and the node fails as `ToolExecutionError` (lines 4370–4375). The default sender it wraps (`_default_webhook_sender`, line ~2945) puts only the caller's headers on the request, so it never sends an idempotency key, and it lets `httpx` exceptions propagate, which are not the builtin `ConnectionError`s of `_DEFINITIVE_EFFECT_FAILURES`: in practice every transport failure there is ambiguous. (A builtin `ConnectionResetError` or `BrokenPipeError` is also listed as "definitive" although it can happen after a commit.) For a downstream that supports a stable key, a send with the same key is safe at the downstream, so #520 must replace "indeterminate, give up" with a question to the downstream (query by key) before any further send; #626 builds the `unknown` state and `reconcile` for that, and its transition table makes the bare re-dispatch of an `unknown` proposal illegal on purpose (this spike's test replays with the bare `send`, which proves the downstream behavior, not a state transition).
- `caliber/src/caliber/workflows/effect_ledger.py::effect_key` (line 123). The platform already has an attempt-invariant key, `eff-<56 hex>` over a fingerprint that includes an `occurrence` counter and canonicalises with `ensure_ascii=False, default=str`. The spike's key is a plain sha256 over `run|node|canonical args` with compact separators and no occurrence. The two will disagree on the same effect. #520 should decide one: either reuse `effect_key` (and carry `occurrence` into the proposal) or replace it and migrate the ledger's key column. The spike does not settle which; it shows only that a stable key suffices for the downstream.
- The two call sites of `_perform_guarded_effect` (the webhook and API-request nodes) are the only **ledger-guarded** seams today (`docs/architecture/protected-effect-paths.md` EP-001, EP-002); the inventory lists 39 `dispatch` rows in all, among them the OpenAPI executor (EP-030, no ledger) and MCP. The sync run route attaches no ledger, so it would repeat the effect on a retry.
- The spike's unique `logical_key` makes a second proposal for identical arguments an `IntegrityError` (tested). The platform's `effect_key` carries an `occurrence` counter precisely so a loop that posts the same body twice is two effects; #520 must carry `occurrence` into the key or a legitimate repeat would be rejected as a duplicate.
- The connector experiment (`docs/reports/egi/D1-connector-capability.md`, #567) has the executor-side findings (key plumbing, retry gating, typed errors) that complement these.

### What surprised me

- The downstream's `If-Match` guard alone already refuses a blind second dispatch with a different key (412), because the first commit bumped the case version. It does not help with a lost response: the retry is refused instead of getting the stored answer, and the caller cannot tell "my first attempt committed" from "someone else changed the case". Only the stable key resolves that, so the key is not redundant with the version check (`test_the_expected_version_alone_also_stops_a_blind_second_dispatch`).
- The proposal row must be set to `dispatched` and committed *before* the request leaves; if it were set after, a crash during the call would leave `proposed`, indistinguishable from "never sent".
- A unique `logical_key` column makes proposing the same effect twice an integrity error on both dialects: a duplicate proposal is rejected by the store, not by application code.
- `validate_record("proposal", ...)` (#566) is cheap enough to call on every proposal, and the spike's proposal record validated against the schema on the first run, so the schema fits the fields a dispatch needs (`logical_key`, `intent_hash`, `target`, `expected_resource_version`, `state`).

## B05 prototype

Spike for #626, extending #625: an ambiguous dispatch is recorded as `unknown`, a dependent action is blocked while it is, and the state is settled by asking the downstream by key, including when the dispatching process was killed after the downstream committed. Code: `caliber/tests/egi_scenarios/prototype/dispatch_spike.py` (`STATES`, `TRANSITIONS`, `transition` with a compare-and-set, `send`, `dispatch`, `dependent_action`, `reconcile`, a `downstream_request_id` column) and `prototype/dispatch_child.py`; tests: `caliber/tests/egi_scenarios/test_prototype_unknown_reconciliation.py` (47 cases, SQLite and PostgreSQL). Both are disposable; #522 deletes them after copying what it needs (below) into `caliber/src/caliber/effects/records.py` and `test_v07_restart_exactly_once.py`.

**Result.** The kill test passes on both dialects: the child process dispatches against a downstream armed to answer 20 s late (its own client timeout is raised to 60 s for the test, so the delayed answer, not the client, bounds the window); the test waits until `downstream.mutations() == 1`, kills the child with SIGKILL, and finds the proposal still `dispatched` (the dead process could not record anything). The test moves it to `unknown` (as a recovery loop would), a dependent action raises `UnknownEffectError`, and `reconcile` asks `GET /document-requests?idempotency_key=<key>`, finds the stored request, checks it is the one the proposal meant (same case and document type, with a request id), records its `downstream_request_id` (equal to what the downstream reports) and moves the proposal to `committed`, with `mutations() == 1`. A blind second dispatch of an `unknown` proposal is an illegal transition. A key the downstream does not know reconciles to `failed`. Three further ambiguous outcomes were exercised and all end `unknown` then `committed`: a dropped response, a **read timeout** after the commit, and a **502 with an HTML body** after the commit (a proxy in front of a downstream that did commit).

**Not every non-2xx is a definite "no".** The first draft recorded any non-2xx as `failed`; a 502 after a real commit then left a `failed` proposal and one mutation. The spike now treats only a 4xx (returned before any mutation, such as 412 and 422) as `failed`, and any 5xx or transport error as `unknown`. The executor already treats 429, 500, 502, 503 and 504 as retryable (`executor.py`, `_RETRYABLE_STATUS`, line 47), which is consistent with them being ambiguous, not refused. Also handled after review: a non-JSON body no longer raises out of `dispatch` and leaves the row `dispatched`.

**The state change is a compare-and-set.** `transition` first read the state and then updated by id, so two actors that both read `proposed` could both move it to `dispatched` and both send. The update is now conditioned on the state that was read (`UPDATE ... WHERE state = <current>`); the second actor matches no row and is refused. A thread race is too narrow to hit reliably, so the property is tested by a stale read (`test_a_stale_read_cannot_overwrite_a_newer_state`); the mutation that removes the condition fails it. #522's production version needs the same, and a row lock or `SELECT ... FOR UPDATE` on PostgreSQL is the alternative.

**Effort.** About 1.5 hours of agent wall-clock for the extension, its tests and the review round, on top of #625; agent time, not a person-hour figure.

**Did the connector answer query-by-key within 1 s?** Yes. Through the real OpenAPI executor (#567, `docs/reports/egi/D1-connector-capability.md`) the median is about 4 ms (max about 5.5 ms over 40 runs); the spike's own `reconcile` (a plain `httpx` GET) is asserted under 5 s, a bound chosen so a loaded CI runner cannot fail it, not a measurement. The spike queries with `httpx` directly; production reconcile must use the connector's query operation. The measurement script for the dispatch numbers is `prototype/measure.py`.

### What #522 must add that the spike lacks

- **The contract's states.** `proposal.v1` (ADR 0003) has seven states: `proposed, approved, dispatched, committed, failed, unknown, reconciled`. The spike's `STATES` has five (no `approved`, no `reconciled`) and its table settles `unknown` straight to `committed` or `failed`. #522 task 2's table (`unknown -> reconciled -> committed | failed`) is the contract; the spike's is a simplification and must not be copied as it stands. The spike validates only the initial `proposed` record against the schema, not later states.
- **Receipt verification.** `reconcile` trusts a 200 once the case and document type match. A receipt (`receipt.v1`, `verified_by: query`) also needs the downstream's request id, a digest of the response and the version it produced; a stored request under the same key with different content (the downstream answers 422 to a reused key) must become a conflict, not `committed`.
- **404 does not prove the effect never happens, and the spike does not fence.** `reconcile` turns a 404 into `failed`. The proposal's state stops *this* dispatcher from sending new attempts; it does not stop a request already in flight at the downstream or sitting in a hung or killed process's socket, which may commit after the query. The spike keeps no tombstone for the key, no downstream-side cancel, no bounded wait, and none of `dispatched_at`, `unknown_at` or an owner column. #522 therefore needs: those columns (a loop finds "`dispatched` for longer than the lease" with them), a rule that `failed` is concluded only after the maximum time a request can still be in flight has passed (or the downstream cannot say), and `unknown` kept until then.
- **Ownership of the recovery loop (B13, #537).** The spike reconciles from a test. In production a loop finds `unknown` proposals; two processes running it would reconcile the same key twice. The compare-and-set makes the second settle a refused no-op, but the loop must treat "already settled" as success and run under the execution-owner lease of ADR 0002.
- **Migration of the legacy ledger.** `caliber_effect_ledger` rows left `in_progress` by a dead process are today surfaced as `IndeterminateEffectError` and cleared by an operator through `resolve_effect` (`workflows/effect_ledger.py`, line ~354). Those rows are exactly the spike's `unknown` and have no proposal. #522 must either backfill proposals for open rows or keep the ledger path for legacy runs and mark them `legacy: true` (`run_manifest.v1`).
- **Distinguishing "never left" from "may have committed".** The spike treats any `httpx.HTTPError` as `unknown`, including a refused connection that never left. The executor flattens both into one `OpenApiExecutionError` with the cause chained (connector report, change 4), so #522 depends on a typed signal there.
- **The `occurrence` counter.** The spike's unique `logical_key` makes a second proposal for identical arguments an `IntegrityError`; the platform's `effect_key` has an `occurrence` precisely so a loop that posts the same body twice is two effects. #522 must carry `occurrence` into the key.
- **Evidence timestamps and attempts.** Neither when a proposal became `unknown` nor how many attempts there were is recorded; the evidence package (#538) needs both.
- **Persistence and isolation.** The spike's table has no tenant, region or project column and no run-level lock; the production record is `proposal.v1` plus the state and receipt tables of ADR 0002, written only by `effects/`.
- **What the kill test cannot show.** It kills the process after the commit and before the answer. A process that dies *between* receiving the answer and recording `committed` is the same case from the platform's side (the proposal is `dispatched`, the downstream committed) and is covered by the same reconciliation; it is not a separate test here.

### What surprised me

- The transition table forbids the most tempting recovery, "just dispatch again": `unknown -> dispatched` is not allowed, so recovery is only ever a question to the downstream. That changed the meaning of #625's test: the same-key replay is still proved (through `send`, the bare call), but it is not a state transition.
- SIGKILL leaves the proposal `dispatched`, not `unknown`: only a recovery path can say "this was in flight when its process died", so `dispatched` older than the lease is the signal a loop looks for, which is why the timestamp columns above matter. A design that waits for the process to record `unknown` itself would never see it.
- With `delay_response_seconds` the downstream commits first and then waits, so the kill window is wide (the 20 s delay, with the child's client timeout raised past it) and deterministic: the test polls `mutations()` rather than sleeping. With the spike's default 5 s client timeout the child would have turned the row `unknown` itself after 5 s, which a first version of the test would have hit on a slow runner.
- A 502 after a real commit was the case that showed `failed` is only safe for a 4xx.

## Re-estimate

Budgets for B04 (#520) and B05 (#522) from the D1 evidence instead of the gap-analysis midpoints. Both packages carried **3 PW** each (6 PW together, one PW being five person-days). The estimates below are in person-days of focused work by one engineer who knows the codebase, including tests, the independent review pass and CI; they are my reading of the prototype and the code, not a measurement of any person's speed, and the three owners tick the PR to confirm them.

Evidence: the inventory has **127** protected-effect rows (39 `dispatch`, 24 `refuse`, 64 `exempt`; `docs/architecture/protected-effect-paths.md`); the B04 and B05 spikes ran on both dialects (sections above); the connector experiment (`D1-connector-capability.md`) found the connector sufficient (`keep`) with five executor changes. Reading across them:

- **Savings.** The propose, key, dispatch sequence, the `unknown` state, the kill-and-reconcile scenario and the connector's query-by-key are proven, so no feasibility risk remains on the hard path; the transition table and the key derivation are copied rather than designed.
- **Added work the prototypes found.** The executor changes (retry only when a key is sent; one way to supply the key; a first-class expected version; retry and key binding reachable from an import; typed transport errors), the seven-state contract against the spike's five, a compare-and-set for every transition, treating a 5xx as `unknown`, a fence before a 404 becomes `failed` (with `dispatched_at`, `unknown_at`, owner columns), backfilling or segregating legacy ledger rows, and the `occurrence` counter in the key. The two roughly cancel.
