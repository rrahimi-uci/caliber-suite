Cookbook 03 · Foundations

Policy-Safe Decision Tool

A deterministic refund policy hardened against 49 fixtures, then a refund that only a second person can release.

FoundationsCore15–30 min
What you build. A refund policy as a registered read tool (decide_refund: approve, deny or manual review, with a stable reason code) and a write tool (initiate_refund, registered with requires_approval). You run them in the sandbox, save a 49-case fixture suite, pin a baseline and catch one deliberate regression, then import the refund-decision workflow that decides, routes, and issues the refund only after a different person approves and the run is resumed. No model is involved: nothing here is simulated.
Surfaces: Tools Workflows Administration Audit Log Cookbooks
What you learn
  • Register a read tool and a write tool: Write locks Requires Approval on, and a write tool registered without it is refused with 400
  • Sandbox: the read tool runs live in a subprocess, the write tool is mocked (Success (mocked))
  • Save 49 fixtures, Run calibration (Pass rate 100% — 49/49 passed), pin the run as the baseline, then break R09 and read 1 regression (48/49)
  • Import the workflow and Run it: the run stops at Awaiting approval on the refund node; the initiator is refused with 403, approver1 approves, and the refund fires only after Resume
  • Reject (approval_rejected, no refund), deny (completes without approval), and read who approved what in the Audit Log
  • Where the sandbox stops being a boundary: a stalled tool is killed, a large write is refused, the environment is empty, and the network is still reachable

Step-by-step UI only

Each step shows the exact navigation path, the fields to fill, the button to click, and a snapshot of the CALIBER screen you'll be on.

  1. Tools › Register Tool creates · tool: decide_refund (read) decide-refund.tool.json ↓
    Register the policy tool. The wizard has five steps: Identity, Implementation, Schema, Playground, Safety & Review. A registered tool must point at importable Python, so you give a Module Path and a Callable Name from the shipped demo module. On the Schema step use each schema's Raw JSON toggle and paste input_schema and output_schema from the asset.

    Version1.0
    Module Pathcaliber.workflows.demo_tools
    Callable Namedecide_refund
    Side effect levelRead (the default)
    Allow in Previewon, so the sandbox runs the real callable
    Click Register Tool
    You'll see: The tool opens in its workspace. Back in the Tools list its row has no Built-in or Unavailable label: those mark CALIBER's own tools. The address becomes /tools?tool=TL-…, so a reload keeps you there.
    Screen snapshot
  2. Tools › Register Tool creates · tool: initiate_refund (write) initiate-refund.tool.json ↓
    Register the write tool the same way. On the Safety & Review step click Write: Requires Approval switches on and is locked, because the registry refuses a write tool without it. (Through the API that refusal is an HTTP 400.)
    Fill in

    Version1.0
    Module Pathcaliber.workflows.demo_tools
    Callable Nameinitiate_refund
    Side effect levelWrite
    Click Register Tool
    You'll see: initiate_refund is registered with Requires Approval on and cannot be turned off.
    Screen snapshot
  3. Tools › decide_refund › Sandbox
    Open the tool from the Tools list, then the Sandbox tab. Run the policy with the first fixture's inputs. Then open initiate_refund and run it: a write tool is never called in the sandbox.
    Fill in
    Input JSON (decide_refund){"order_id": "ord_1007", "account_id": "acct_2013", "order_state": "delivered", "amount": 49.0, "days_since_order": 5, "customer_tier": "standard", "refunds_last_90d": 0, "risk_flags": []}
    Input JSON (initiate_refund){"order_id": "ord_1007", "amount": 49.0}
    Click Test Run
    You'll see: Success with decision: approve, reason_code: ELIGIBLE_AUTO_APPROVE. For the write tool: Success (mocked) and the output {"_preview_mock": true}.
    Screen snapshot
  4. Tools › decide_refund › Fixtures creates · tool fixtures: refund-fixtures refund-fixtures.jsonl ↓
    Load the 49 cases from the dataset file: Load cases from file, choose refund-fixtures.jsonl. Each line becomes a case named R01 small delivered order, with the line's inputs as the input JSON and an equals assertion on its expectations (key order and spacing do not matter). Loading only fills the editor; nothing is stored until you save. You can also add or edit single cases by hand with Add case.
    Click Save cases
    You'll see: Loaded 49 cases from refund-fixtures.jsonl. Save cases to keep them., then Saved after you save, and 49 case rows in the editor (still 49 after a reload).
    Screen snapshot
  5. Tools › decide_refund › Hardening
    Run the saved suite. It scores inline, one subprocess per case, so 49 cases take about half a minute. A run is recorded under Test Runs automatically.
    Click Run calibration
    You'll see: Pass rate 100% — 49/49 passed and a green pass on every case.
    Screen snapshot
  6. Tools › decide_refund › Test Runs
    Open Test Runs and pin the latest run. Then go back to Hardening, change the expected value of case R09 (approve) to manual_review / AMOUNT_OVER_THRESHOLD / true, and run the suite again. Put the value back afterwards and run once more.
    Click Set as baseline then Run calibration
    You'll see: The pinned run carries a Baseline marker. The second run reads Pass rate 98% — 48/49 passed; under Test Runs the comparison shows 1 regression on R09 and Net score -2%.
    Screen snapshot
  7. Workflows › Import creates · workflow: refund-decision refund-decision.workflow.yaml ↓
    Import the workflow asset. If you registered the tools under other names, replace decide_refund and initiate_refund in the file first. Validate dependencies checks that both tools resolve.
    Fill in
    New workflow namerefund-decision
    YAML/JSON manifestChoose file: refund-decision.workflow.yaml
    Click Validate dependencies then Import as new
    You'll see: Preflight passed, both tools resolved; then the editor opens on the new draft.
    Screen snapshot
  8. Workflows › refund-decision › Run Monitor
    Run a case, then try to approve it yourself. In a second browser session sign in as approver1, pick the same workspace, open the workflow, Run Monitor, select the run in Recent runs and approve. Back in the first session, Resume. The gate is the refund tool's own approval flag.
    Fill in
    Run inputthe R01 inputs, as in the Sandbox step
    Click Run then Approve then Approve then Resume
    You'll see: The run stops at Awaiting approval on node refund. Your own Approve is refused (a second person must decide). After approver1 approves, Resume enables; after it the run is completed and the output shows refund_status: initiated, amount_usd: 49.0.
    Screen snapshot
  9. Workflows › refund-decision › Run Monitor, then Audit Log
    Start two more runs: one with the R01 inputs that approver1 rejects, one with the R23 inputs (a cancelled order). Then open Audit Log.
    Click Run then Reject
    You'll see: The rejected run is failed and its output holds no refund. The R23 run completed with decision: deny and never asked for approval. Audit Log lists approve_workflow_run_runtime_approval and reject_workflow_run_runtime_approval by approver1, and resume_workflow_run by the initiator.
    Screen snapshot
  10. Tools › decide_refund › Publish
    Open decide_refund, tab Publish, Version history, New version (admins). The wizard opens with the name fixed and the version 1.1; change the description and step through to Register. In the new workspace open Fixtures, Load cases from file (refund-fixtures.jsonl again), Save cases, then Hardening and Run calibration.
    Click Run calibration
    You'll see: Pass rate 100% — 49/49 passed on version 1.1. Publish lists 1.0 and 1.1 under Version history, and the Tools list shows both under the one name.
    Screen snapshot

Developer notes & gotchas
  • Feature flag. CALIBER_FEATURE_COOKBOOKS=true only opens the Cookbooks gallery starter (the last step); the rest of the lab needs no flag. No Aria, integrations or release-candidate flag.
  • Nothing is simulated. No model and no judge are involved, so the fake LLM provider is irrelevant here.
  • Runtime settings. Needs runtime approvals, the workflow run queue, checkpointing and a worker (scripts/cookbook-env.sh turns them on). Without CALIBER_WORKFLOW_RUN_RUNTIME_APPROVALS_ENABLED=true a run does not pause. CALIBER_APPROVER_USERS must list approver1; leave CALIBER_APPROVAL_ALLOW_SELF_APPROVAL unset or the second-person rule does not bite.
  • Split of duties. Run, calibrate and Resume need caliber.operator; deciding needs caliber.approver; only an admin registers a tool. approver1 deliberately cannot Resume.
  • Tools are importable Python. A registered tool needs a module_path and callable_name in the server's environment (the shipped caliber.workflows.demo_tools provides both); there is no inline tool editor. Set CALIBER_REGISTERED_TOOL_MODULE_ALLOWLIST beyond a trial.
  • Limits. The sandbox is a process boundary, not isolation (the child keeps network and filesystem access), and the memory limit is not enforced on macOS. The effect ledger covers webhook and API-request nodes, not registered tools, so make a payments tool idempotent itself.
  • Calibration is slow. 49 cases take about 35 s synchronously, longer than the SDK default 30 s timeout. Run it with sdk/caliber-sdk/examples/cookbooks/cookbook_03_policy_safe_decision_tool.py (python -m examples.cookbooks.cookbook_03_policy_safe_decision_tool) or the Playwright spec e2e/cookbooks/labs/03-tool-hardening.spec.ts.
