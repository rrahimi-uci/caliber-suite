Cookbook 02 · Foundations

Precision Skills

A support-tone skill measured on 40 trigger cases (30 right, then 40), calibrated, applied, rolled back, packaged and archived.

FoundationsStarter45–75 min
What you build. A narrow skill, support-tone-and-citation, that gives customer-facing support replies one voice (calm, no over-promising, cited knowledge-base ids, an escalation hint) and must not fire on engineering work. You run a 40-case trigger set against the real, deterministic skill selector, tighten the trigger phrases, pin the baseline, then calibrate, review, Apply and roll back, export and re-import it as a ZIP package, try the failure paths and archive it. Needs only CALIBER_FEATURE_COOKBOOKS=true; calibration is simulated.
Surfaces: Cookbooks Skills Administration Audit Log
What you learn
  • Author a skill in Build Skill: the selector reads name, tags, summary and trigger phrases, never the long-form content
  • Render Preview: variable substitution, and what stays unresolved (a partial set shows 2 unresolved)
  • Run the 40 trigger cases: the six starter phrases get 30/40 right (8 false positives, 2 false negatives); tightened phrases (3 should-trigger, 14 should-not-trigger) get 40/40
  • Pin that run as the baseline, Calibrate, read the review (Simulated evaluation — not evidence, 0 evaluation examples), Apply to skill (v2), then Roll back (v3 with the text of v1)
  • Download ZIP, then Import ZIP with reject (409), rename or merge: the package holds the instructions, not the tags, category or trigger phrases
  • Failure paths: invalid content (400, duplicate name 409), a calibration with no baseline (still works), a viewer's Apply, Calibrate, Roll back and Create (403)

assets/skills/support-tone-and-citation.md 
---
name: support-tone-and-citation
summary: "Voice and citation rules for customer-facing support replies (billing, refunds, account, how-to); NOT for engineering, code, API, infra, or schema questions."
category: customer_support
tags: [support, tone, citation, escalation, customer-facing]
should_not_trigger: [stack trace, signing key, database index, sql migration, latency metrics, unit test]
render_variables: [user_message, audience, policy_context]
---

You shape how a support reply is written. You do NOT decide the underlying
policy outcome (refund approved/denied, account unlocked, etc.) — that decision
arrives in `{{ policy_context }}`. Your job is to deliver it to the customer in
the right voice, with the right citations and the right escalation hint.

Apply this only to **customer-facing support replies**. If the request is an
engineering, code, API, infrastructure, database, or internal-tooling question,
this skill does not apply — defer to the relevant engineering skill instead.

## Tone rules

- Stay calm and plain-spoken. Acknowledge the customer's situation in one
  sentence before getting to the answer; do not gush or over-apologize.
- Write for `{{ audience }}`. A non-technical customer gets no product
  internals; a technical contact may get precise field/feature names but still
  no internal system names.
- No internal jargon. Never expose internal team names, ticket/queue ids,
  service or component names, codenames, or model/provider names.
- No over-promising. Do not commit to dates, amounts, or outcomes that are not
  already stated in `{{ policy_context }}`. If something is "under review", say
  exactly that — never "this will be fixed" or "you'll get a full refund"
  unless `{{ policy_context }}` says so.
- One ask at a time. If you need information from the customer, request a single
  clear thing.

## Citation hints

- When you assert a fact, a policy, or an eligibility rule, cite the supporting
  knowledge-base article by id (e.g. `[KB-1042]`) inline right after the claim.
- Only cite article ids that appear in `{{ policy_context }}`. Never invent a
  KB id, and never cite an id you were not given.
- If `{{ policy_context }}` contains no supporting article for a claim, soften
  the claim to what you can support and add: "I'm confirming the exact policy
  and will follow up." Do not fabricate a citation to fill the gap.

## Escalation hints

- Escalate (hand to a human/specialist) when `{{ policy_context }}` is empty or
  contradictory, when the customer is at financial or security risk, or when the
  resolution requires an action this reply cannot itself authorize.
- When escalating, tell the customer plainly that you are routing them to
  someone who can help and set a realistic next-step expectation — without
  naming the internal team or queue.

## Output

Produce only the customer-facing reply text. No headers, no internal notes, no
JSON. End with a single concrete next step or a clear closing line.

Audience: {{ audience }}
Policy context (decision + any KB article ids to cite):
"""
{{ policy_context }}
"""
Customer message:
"""
{{ user_message }}
"""

Write the reply now.

Developer notes & gotchas
  • Feature flag. CALIBER_FEATURE_COOKBOOKS=true only opens the Cookbooks gallery; Skills work without it. No Aria, integrations or release-candidate flag is needed.
  • What is simulated. Trigger selection (test-selection) is deterministic code and real on every stack; there is no LLM judge. Calibration is simulated by default (canned 0.94 vs 0.88, provider: fake); n_examples is 0 because a skill has no test set, so the 40 cases score selection only. It proves wiring, not that the candidate is better.
  • Selector gotchas. One summary word is enough to select; a positive sharing no word with name, tags or summary is not selected (T14, T23). A matching should-not-trigger phrase ends the score at 0. Fix misses with phrases, never content edits; scores depend on the skill name, so assert decisions, not scores.
  • Package limits. A package carries instructions only: the copy gets category custom, no tags, no trigger phrases and a 64-character summary, so its decisions differ (13 cases in the run) until you restore them. A merge import (admin only) overwrites the summary with the shortened one.
  • Roles and names. Create needs operator; patching metadata and rolling back need admin. Names are kebab-case, must not start with claude or anthropic, are unique across the deployment, and an archived skill keeps its name.
  • Background worker. Calibration stays queued unless CALIBER_BACKGROUND_TASKS_ENABLED=true (set by scripts/cookbook-env.sh). Scenario Sets live in the page and clear on leaving it.
  • Not covered. The Bind stage, a calibration that improves the skill, project roles other than Viewer, and Aria choosing the skill.
