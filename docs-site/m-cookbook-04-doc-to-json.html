Document-to-JSON Pipeline

Turn invoice documents into schema-checked JSON, and hold every invalid one for a second person to approve or reject.

BuildCore20–30 min
What you build. A workflow that reads one invoice from the doc-intake bucket, extracts JSON with a deterministic python_code node, and checks it against a JSON Schema with a data_transform json_schema node. A valid record is written to doc-extracted under invoices/<invoice number>.json; an invalid one stops at review_gate, where a second person approves it (written under reviewed/) or rejects it (nothing is written). No model is called, so simulated and real providers give the same result.
Surfaces: Object Store Cookbooks Workflows Administration
What you learn
  • Create the doc-intake and doc-extracted buckets, upload the 30 sample documents under incoming/ and preview one in Object Store
  • Install the Document-to-JSON Pipeline cookbook as a paused draft from Cookbooks, then Resume it
  • Run one document per queued run, with the object key as the run input, and read each step in the Execution Debugger
  • See a duplicate invoice refused by the output bucket, and hold a document that fails the schema at an approval gate
  • Approve and reject as the reviewer account; the account that started a run is refused (403)
  • Check what reached the output bucket: exactly 17 objects, and nothing for the rejected document

Implementation flow

flowchart LR
  IN[("Bucket doc-intake: incoming/")] --> RD["read_document"]
  RD --> EX["extract_fields: python_code"]
  EX --> VS["validate_schema: JSON Schema"]
  VS --> PK["package_result"]
  PK --> RT{"route"}
  RT -->|valid| EE["emit_extracted"]
  EE --> WE[("write_extracted: doc-extracted/invoices/")]
  RT -->|invalid| RG{{"review_gate: second person"}}
  RG -->|approve and resume| WR[("write_reviewed: doc-extracted/reviewed/")]
  RG -->|reject| FAIL["run fails, nothing written"]

Developer notes & gotchas
  • Flags. CALIBER_FEATURE_COOKBOOKS=true opens the gallery (a preview area, off by default); no other flag is needed. The lab also needs an S3-compatible store: scripts/cookbook-env.sh up lab04 --flags cookbooks --s3 starts a private in-memory one, so objects do not survive restart.
  • Nothing in the pipeline is simulated, and no model is called. The simulated default LLM and evaluator providers are never used; the result is deterministic. The object store is real S3 protocol (moto), not a production service.
  • Second person required. Start with CALIBER_APPROVER_USERS=admin,reviewer CALIBER_OPERATOR_USERS=admin,reviewer (approver to approve or reject, operator to resume). Leave CALIBER_APPROVAL_ALLOW_SELF_APPROVAL unset, and keep runtime approvals and the run queue on.
  • Text only. input_bucket decodes UTF-8 with replacement characters and keeps 100,000 bytes per object, so binary .docx/.xlsx cannot flow through it, and the 120 KB oversized file is truncated.
  • Preview is blocked. The editor's Preview refuses this workflow (it cannot isolate python_code, input_bucket or output_bucket); run it for real, queued, through POST /workflow-runs.
  • Extractor is rules, not a model. It understands only the layouts in the corpus (aligned text, Markdown table, CSV) and writes null for anything a document does not state. A new layout is a new dataset case and a new rule. One run handles one document.
  • Keep the gate's shape. After an approval only what flows through the gate reaches later nodes; the installed workflow puts the record and its schema errors in one text (package_result) for that reason.
  • Runnable. sdk/caliber-sdk/examples/cookbooks/cookbook_04_document_to_json_pipeline.py (about 75 s, 30 runs); UI: caliber/caliber-ui/e2e/cookbooks/labs/04-document-extraction.spec.ts; environment: scripts/cookbook-env.sh up lab04.
