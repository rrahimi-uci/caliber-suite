Release Signoff Factory

Record an accountable go / no-go: server-scored criteria, owned waivers, an immutable signoff. A record, not a deployment.

GovernCore20–40 min
What you build. You create 20 release candidates from a dataset and check the server's weighted score, status and blockers against figures worked out independently (14 ready, 6 blocked). On a few of them you record admin waivers, generate an Allure-compatible report snapshot and sign off GO and NO-GO, then see that a signed candidate is final. Releases is a preview, record-only page: signing off writes a decision and deploys or rolls back nothing. No model is involved, so nothing is simulated.
Surfaces: Releases Audit Log
What you learn
  • Create candidates with weighted criteria and read the server-computed weighted_score, status and blockers; ready means score at or above required_score and no unwaived blocker
  • Record an admin waiver (existing criterion key, reason of 8 or more characters, future expiry): it clears a blocker but never a low score
  • Generate Allure after the last change, because a report made earlier is a stale snapshot with a different SHA-256
  • Sign off GO or NO-GO with a rationale; a signed candidate cannot be evaluated, waived or signed again (409)
  • See that a signed GO moves no alias and adds nothing to the timeline; Promote on the prompt is the real release
  • Read who created, waived, reported and signed in the audit log

Implementation flow

Evaluation & quality gates

Quality gateTarget
Candidates created20, server score, status and blockers equal the dataset (14 ready, 6 blocked)
WaiverRC16 becomes ready at the same 0.721; RC17 stays blocked (0.6575) after both blockers are waived
GOrefused (409) on a blocked candidate and on one with no planned action or rollback target
After signoffevaluate, waive and a second signoff are refused (409)
Signoff deploys nothingprompt aliases, live board and timeline unchanged; only Promote moves the alias
Developer notes & gotchas
  • Feature flags. CALIBER_FEATURE_RELEASE_CANDIDATES=true shows the Release signoff factory section on Releases and enables /releases/candidates (404 feature_disabled without it); CALIBER_FEATURE_COOKBOOKS=true is only for the gallery. Both are preview areas, off by default. Start with scripts/cookbook-env.sh up lab11 --flags release_candidates,cookbooks.
  • Scopes. Creating, re-evaluating and reporting need the operator scope (CALIBER_OPERATOR_USERS); waivers and signoffs are admin-only (403 otherwise).
  • The scores are typed in. CALIBER does not read them from Evaluations, Review Queues or traces, and does not open evidence references or check that the artifact exists; a candidate for a missing artifact is accepted.
  • The report is a snapshot. Allure-compatible JSON with a SHA-256 of the candidate at that moment, not a CI test report; generate the one you keep after the last waiver.
  • A waiver does not raise a score, and there is no route that edits a candidate: create a new candidate for new evidence. The UI form has no expiry field, so write the expiry into the reason (the API takes expires_at).
  • Candidates cannot be deleted. Those created outside a workspace are private to their creator, so a viewer does not see the admin's list.
  • Run it with sdk/caliber-sdk/examples/cookbooks/cookbook_11_release_signoff_factory.py or the Playwright spec caliber/caliber-ui/e2e/cookbooks/labs/11-release-signoff.spec.ts.
