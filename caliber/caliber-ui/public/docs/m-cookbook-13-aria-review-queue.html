Aria: Human-Review Queue from Intent

One sentence → a rules-based Aria plan creates a review queue and enqueues 30 flagged traces; people review 12, and the answers land on the traces as labelled examples.

Aria — AutonomousAria15–30 min
What you build. You give Aria one sentence, Set up a review queue for human labeling of agent replies for safety, citation, and tone., and it draws two steps: review_queue.create then review_queue.add_items. You enter the queue's name and five-question schema (safety, severity, citation_ok, tone_ok, reviewer_notes) in the plan's form; the enqueue form asks only for trace_ids because the queue's id is wired from step 1. The result is an active queue with 30 pending traces; 12 are reviewed, each answer becomes an assessment on its trace and a labelled example for judge alignment (lab 10).
Surfaces: Plans Review Queues Observability
What you learn
  • Plan a governance queue from one intent on Integrations > Plans, and see why a review queue always brings its review_queue.add_items step (skip it if you have no traces)
  • Enter a queue's question schema (pass_fail, categorical, numeric, text; fields key, title, type, options, required, target) in the plan's Aria needs information form
  • See dependency wiring: the enqueue step's only wired input is queue_id from the create step, so its form asks for trace_ids and assigned_to only
  • Review items in Operate > Review Queues (Submit review); answers are validated against the questions (400 on a mismatch, item stays pending) and written to the trace in Observability
  • Read the refusals: a skipped queue skips the enqueue, a denied enqueue keeps an empty queue, a categorical question with no options fails the plan, a taken name fails the plan, an account without the operator scope creates nothing

# The intent you give Aria

## Canonical (works with the default planner)

> Set up a review queue for human labeling of agent replies for safety, citation, and tone.

Why this wording: the default planner proposes a step for each capability whose
**domain word** appears in the goal. "review queue" gives `review_queue.create` **and**
`review_queue.add_items` (same domain). Keep the words "review queue" (with a space) in
the sentence.

Autonomy: **Stop before each change** (`ask_each`: an **Approve** / **Deny** prompt
before every step that changes something, after the input form).

## What the planner does with other sentences

`dataset/goals.jsonl` holds 26 goals and the plan the server draws for each one; the
script checks all 26 against the real server. In short:

- Any sentence with `review queue` plans both the queue and its enqueue step, however it is
  phrased. If you have no traces yet, **Skip step** (or **Deny**) the enqueue; the queue is
  still created. Skipping the queue's own form skips the enqueue with it.
- `review-queue` (hyphen) and `reviewqueue` plan nothing; neither does "human review" or
  "human grading": the planner looks for the exact words, there is no language model behind it.
- It does not read negation (`Do not create a review queue...` still plans one), a question
  (`What is a review queue?`) or a request to delete one: there is no delete capability.
- A sentence with no domain word makes a plan with no steps; it cannot be approved
  (HTTP 409).

assets/seed_traces.py 
#!/usr/bin/env python3
"""Record the 30 flagged agent replies as MLflow traces, so a review queue can hold them.

In a real deployment these traces are produced by your agent and flagged by thumbs-down, a keyword
rule or a low judge score. A fresh checkout has none, and Operate > Review Queues works on traces,
so this script writes one trace per row of ``dataset/agent-replies.jsonl``: the request is the
customer's message, the response is the agent's reply, and the tags say which row it is
(``cookbook13.row``, R01..R30) and why it was flagged (``cookbook13.flag``).

Needs the ``mlflow`` package and ``MLFLOW_TRACKING_URI`` (the MLflow server CALIBER uses).
Prints a JSON map ``{"R01": "<trace_id>", ...}`` on stdout. Every run writes 30 new traces, so
run it once per environment.

    MLFLOW_TRACKING_URI=http://127.0.0.1:5000 \
      python docs-site/cookbooks/13-aria-review-governance-queue/assets/seed_traces.py > traces.json
"""

from __future__ import annotations

import json
import sys
from pathlib import Path

DATASET = Path(__file__).resolve().parent / "dataset" / "agent-replies.jsonl"
EXPERIMENT = "cookbook-13-flagged-replies"


def seed(dataset: Path = DATASET) -> dict[str, str]:
    """Write one trace per row and return ``{row id: trace id}``."""
    import mlflow

    mlflow.set_experiment(EXPERIMENT)
    trace_ids: dict[str, str] = {}
    for line in dataset.read_text(encoding="utf-8").splitlines():
        if not line.strip():
            continue
        row = json.loads(line)
        with mlflow.start_span(name="agent-reply", span_type="CHAIN") as span:
            span.set_inputs({"user_message": row["user_message"]})
            span.set_outputs(row["reply"])
            trace_id = span.trace_id
        mlflow.set_trace_tag(trace_id, "cookbook13.row", row["id"])
        mlflow.set_trace_tag(trace_id, "cookbook13.flag", row["flag"])
        trace_ids[row["id"]] = trace_id
    mlflow.flush_trace_async_logging()
    return trace_ids


if __name__ == "__main__":
    json.dump(seed(), sys.stdout, indent=2)
    sys.stdout.write("\n")

Developer notes & gotchas
  • Flags. CALIBER_FEATURE_ARIA=true opens /aria/* and Plans (404 feature_disabled without it); CALIBER_FEATURE_COOKBOOKS=true is only for the gallery card. scripts/cookbook-env.sh up lab13 --flags cookbooks,aria with CALIBER_OPERATOR_USERS=admin,olga exported first (vera must not be an operator).
  • No model anywhere. The planner is rules (same on a real deployment) and review is people's work; the 12 reviews are the labels in assets/dataset/agent-replies.jsonl, submitted by the script. Judge alignment against them needs a real model and is lab 10.
  • Traces are seeded. A fresh checkout has no agent, so assets/seed_traces.py writes 30 MLflow traces (needs mlflow from the dev virtualenv and MLFLOW_TRACKING_URI from env.sh); with your own agent you copy the flagged trace ids.
  • The enqueue does not check ids. A trace id that does not exist is queued (201, pending) and fails when reviewed (502 RESOURCE_DOES_NOT_EXIST); it stays pending. The enqueue does not discover traces either.
  • Queues are personal. A queue created outside a workspace belongs to its owner: an operator listed in reviewers still gets 404, because reviewers is a label, not access. Team review needs a workspace (lab 18).
  • Limits. Aria only creates a queue and adds traces (no edit or delete; change a schema with PATCH /review-queues/{id} or Review Queues). A failed plan cannot be run again (409); plans cannot be deleted.
