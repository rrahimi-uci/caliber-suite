Aria: Governance Starter Kit from Intent

One sentence → a four-step Aria plan creates a judge, a review queue and a Test Set under three names, at two autonomy levels, with the failure behaviour shown.

Aria — AutonomousAria15–30 min
What you build. You give Aria one sentence (Stand up our governance starter kit: a judge for answer faithfulness, an eval dataset to score against, and a review queue for human checks.) and it draws four steps in registry order: judge.create, review_queue.create, eval_dataset.create, review_queue.add_items. Each step asks for its own fields and, under Stop before each change, an approval; you skip the enqueue step (no traces yet). The result is a real judge (AnswerFaithfulness, bool), a queue (governance-review, four questions, no items) and an empty Test Set (release-candidates-eval), which you fill with 30 policy cases.
Surfaces: Plans Judges Test Sets Review Queues Evaluations
What you learn
  • Compose several capabilities in one plan from one intent; the plan follows registry order, not the order of the sentence, and a review queue always brings its enqueue step
  • Fill the judge, queue and Test Set forms and approve each step: seven questions in all (three forms with an approval each, then the enqueue form, skipped); only the enqueue step has a wired input (queue_id)
  • Change a draft's Autonomy to Run everything it safely can before approving (409 after): the same kit is built with only the four forms, no approval prompts
  • See what Deny does (denying the queue skips the enqueue with it) and what a half-failed plan leaves behind (a taken queue name fails the plan after the judge was made; Aria does not undo earlier steps)
  • Verify the kit in Judges, Review Queues and Test Sets, load the 30 cases with + Add example, and see Evaluations refused on the simulated stack

assets/intent.md 
# The intent you give Aria

## Canonical (works with the default planner)

> Stand up our governance starter kit: a judge for answer faithfulness, an eval dataset to score against, and a review queue for human checks.

Why this wording: the default planner proposes a step for each capability whose
**domain word** appears in the goal. "judge" gives `judge.create`; "eval dataset"
(or "test set") gives `eval_dataset.create`; "review queue" gives `review_queue.create`
**and** `review_queue.add_items` (same domain). Keep all three phrases in the sentence.

The plan runs in registry order, whatever the order of the sentence: judge, review queue,
test set, then the enqueue step. There are no traces yet, so **Skip step** on the enqueue form.

Autonomy: **Stop before each change** (`ask_each`: an **Approve** / **Deny** prompt before
every step that changes something, after the input form). Under **Review the plan, then
run** or **Run everything it safely can** the prompts are not asked and only the input forms
remain: the lab runs the same sentence both ways.

## What the planner does with other sentences

`dataset/goals.jsonl` holds 28 goals and the plan the server draws for each one; the script
checks all 28 against the real server. In short:

- "governance", "starter kit", "score for faithfulness", "held-out set", "spot-check" and
  "human review" are not domain words. A sentence that uses only them plans nothing, or only
  the part it does recognise (`Score the release candidate for faithfulness, keep a held-out
  test set, and let a human spot-check the tricky ones.` plans the test set alone).
- `review-queue` (hyphen) plans nothing; `test-set` (hyphen) does plan a test set.
- It does not read negation, questions or "delete", it matches `judge` inside `judgement`,
  and `workflow` plans `workflow.calibrate` (a calibration of an existing workflow, lab 15),
  never a new workflow: Aria cannot build one.
- A sentence with no domain word makes a plan with no steps; it cannot be approved
  (HTTP 409).

Developer notes & gotchas
  • Flags. CALIBER_FEATURE_ARIA=true opens /aria/* and Plans (404 feature_disabled without it); CALIBER_FEATURE_COOKBOOKS=true is only for the gallery card. scripts/cookbook-env.sh up lab14 --flags cookbooks,aria with CALIBER_OPERATOR_USERS=admin,olga exported first (vera must not be an operator).
  • Simulated vs real. The planner is rules (no model, same on a real deployment); the judge, queue, test set and the 30 rows are real. With the default fake LLM/eval providers Evaluations is refused (400 evaluation requires a real LLM provider); a real provider would let the judge score the 30 rows.
  • Three names. Each step asks for its own name; nothing is shared between the judge, queue and test set (an older build linked names). Names are unique across the deployment, archived ones included.
  • Planner limits. Domain words only: judge, eval dataset, test set, review queue, workflow. "Governance", "starter kit" and "spot-check" plan nothing; test-set works but review-queue does not; negation and "delete" are not read; a workflow plans a calibration of an existing one (lab 15), Aria cannot build one.
  • Partial failure. A failed plan cannot be run again (409): state the goal again. What earlier steps made stays; archive it under Judges, Review Queues or Test Sets.
  • Scope. Enqueuing and reviewing traces is lab 13 (this lab skips it); adding the 30 rows is not an Aria capability (UI recipe adds three by hand, the script adds all 30). Plans cannot be deleted.
